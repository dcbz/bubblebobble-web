# Bubble Bobble player physics & animation — ROM model

Source hardware: Taito A78. Fixed chip `a78-06-1.51` (CPU 0x0000-0x7fff),
banked chip `a78-05-1.52` (window CPU 0x8000-0xbfff; physical bank =
(fb40 XOR 4) & 7). Implementation: `web/physics.js`, goldens in
`web/physics.test.js` (`node web/physics.test.js`).

## Coverage correction (predecessor bug)
`analysis/banked-walk-report.txt` (regenerated by `analysis/banked/cover3.py`)
now shows `bank0: 0 reachable` and that is HARDWARE-CORRECT, not a walk
bug: all 40 fixed-ROM bank-select sites (`ld a,N; call 0x026c`) use
N in {1,2,3}; the banked chip contains no `call 0x026c` at all; the idle
restore at `0x029b` maps bank0 while only fixed code executes. Bank0 bytes
never execute. Reachable: bank1 14543/16384, bank2 15525/16384,
bank3 15400/16384.

## Per-frame player loop (fixed ROM 0x4018-0x41e8)
Records `ix = 0xe691` (P1) / `0xe6c3` (P2), stride 0x32:

| offset | meaning | cite |
|---|---|---|
| +0x01 | x pixel, wraps mod 256 | attr bit6, bublbobl_video.py |
| +0x02 | y pixel | |
| +0x03..04 | ptr to cell record (+0 xc, +2 yc); px = cell*16+8 | 0x1537 |
| +0x05/+0x06 | anim frame index / 16-bit timer | 0x43c1, 0x450d |
| +0x08 | facing (0/1) | 0x43a0 |
| +0x0b bit0 | blocked into wall | 0x42a7 |
| +0x12 | anim id: 0 stand, 8 walk, 0x18 climb, 0x30 vertical | 0x427a/0x42ea/0x470e |
| +0x1f | walk-ramp phase | 0x46d4 |
| +0x20 | vx px/frame (from ramp) | 0x46f6 |
| +0x22 | vy in CELL steps/frame | 0x4708 |
| +0x23 | mode 0 ground, 2 walk, 3 climb | 0x4263/0x4274/0x42e6 |
| +0x21/22/24 | zeroed every frame at loop tail | 0x41d7-0x41de |

## Facts encoded in web/physics.js
1. **No jump.** The only reachable writers of vy `[ix+0x22]` are the
   per-frame zero (0x41db) and the two-player proximity bounce
   (`0xe6b3`/`0xe6e5` = ±`[ix+0x20]` within 12x14 px, 0x475b). The dead
   bank0 byte at file 0x12dc is unreachable code. Up/down selects the
   climb path (mode 3, 0x42e3).
2. **Walk speed** = ramp bytes at fixed `0x12bf` (reached via table
   `0x11ce` entry 22 selected at 0x46dc): `02 02 02 02 03 ff` →
   [2,2,2,2,3] px/frame, 11 px / 5 frames = **2.2 px/frame @ 60 Hz**.
   Horizontal collision tests the tile at (x, y+8) per pixel
   (0x4282-0x42a3, nibble lookup 0x174c); blocked sets [ix+0x0b] bit0.
3. **Falling** drops exactly one cell (16 px) per frame while the feet
   tile `(x, y+8)` is empty (0x435d-0x4376, applied via 0x4708). There is
   no gravity accumulation anywhere in reachable code.
4. **Screen wrap**: x mod 256 (sprite attr bit 6 subtracts 256); ladder
   edge compares cp 0x20 / cp 0xe0 at 0x42fc/0x4300 bound the 32..223 px
   inner playfield.
5. **Animation**: walk pattern table fixed `0x4450` (41 entries
   `[dur, flag, char]`): startup 30 ticks at char 0x8c, then cycle
   0x8c,0x90,0x94,0x98 @ 3 ticks; index [ix+0x05] capped 0x1e=30
   (0x43c1). Stand: 2 frames @ 20 ticks (0x4584 entry 0). Sequence table
   fixed 0x4584, 4-byte entries; timer reset helper 0x1556.

## Open questions
- Exact per-iteration semantics of the mode-2 loop at 0x4282 (it
  increments the cell y byte, not x — assumed auto step-down; web model
  steps x per pixel and steps y up once on platform edges per
  0x435d-0x4376).
- Enemy movement/wall-bounce/gravity: code lives in banks 1/3, not yet
  translated; `web/main.js` enemies keep a placeholder vy accumulation.
- Walk-frame sprite chars not exported to `web/assets` yet (only
  `player1`/`player2` single poses), so the cycle drives `animFrame` but
  not distinct images.
- One-way platform behavior from below (0x4395 head test, 0x1604)
  intentionally omitted pending ladder/one-way tile data in the manifest.
